1. **The central difference's error is about $\frac{h^2}{6}f'''$, the forward difference's about
   $\frac{h}{2}f''$.** Expanding $f(x \pm h)$ around $x$, the $h^2$ terms cancel in $f(x + h) - f(x - h)$, so the
   central error is proportional to $h^2$, not $h$. Making $h$ tiny fails because each value of $f$ carries a
   rounding error of about $\varepsilon\lvert f\rvert$; the numerator is a difference of nearly equal numbers, so
   its error stays near $\varepsilon\lvert f\rvert$ while the division by $h$ magnifies it as $\varepsilon\lvert f\rvert/h$.
   The total is U-shaped in $h$. *Revisit: A4.1.*
2. **For a unit direction $\mathbf{u}$, the slope is $\nabla f\cdot\mathbf{u} = \lVert\nabla f\rVert\cos\theta$, largest at $\theta = 0$.**
   So $\nabla f/\lVert\nabla f\rVert$ is steepest uphill, with slope $\lVert\nabla f\rVert$. Along a contour $f$ does not
   change, so the slope is 0, so $\cos\theta = 0$: perpendicular. At a minimum no direction goes down, so
   $\nabla f = \mathbf{0}$. *Revisit: A4.2.*
3. **Each node is visited once forward and once backward, and the backward pass reuses each upstream
   gradient for all of the node's inputs, so one sweep yields every partial derivative of the single
   output.** Finite differences must re-run the whole forward pass for each perturbed parameter. The price of
   reverse mode is memory: all intermediate values from the forward pass must be stored until the backward
   pass uses them. *Revisit: A4.3.*

5. **Convex: $f(t\mathbf{x} + (1 - t)\mathbf{y}) \le t f(\mathbf{x}) + (1 - t) f(\mathbf{y})$ for all $\mathbf{x}, \mathbf{y}$ and $t \in [0, 1]$: the graph

## Part 2: Interview questions

### 1. Explain backpropagation to an engineer who knows calculus. Why reverse mode?

**Strong answer:** A model's loss is a composition of simple operations, which we can draw as a graph: matrix
multiply, add bias, activation, and so on, ending in one number. Backpropagation is the chain rule applied to
that graph in reverse. In the forward pass we compute and store every intermediate value. Then we start from
$\partial\mathcal{L}/\partial\mathcal{L} = 1$ and walk backwards; each node multiplies the gradient arriving from above by its
own local derivative and passes it to its inputs, and where a value fed several nodes, the contributions add.
For vectors each node computes a vector-Jacobian product, like $\mathbf{X}^\top\bar{\mathbf{z}}$ for a linear layer, without ever
forming the Jacobian. Reverse mode suits ML because there is one output and millions of inputs: one backward
pass gives all the partial derivatives for a few times the cost of the forward pass. Forward mode would need
one pass per parameter. The cost is memory for the stored activations.

**Weak answer:** "Backprop is how neural networks learn: the error is propagated backwards through the
network and the weights are updated with gradient descent."

**Why the weak one fails:** it names the algorithm without explaining it (no chain rule, no stored
activations, no local derivatives), conflates computing the gradient with the update step, and says nothing
about why reverse mode is efficient.

**Follow-up an interviewer would ask:** "Why does training use much more memory than inference, and what is
gradient checkpointing?"

### 2. Your training loss becomes `nan` after a few hundred steps. How do you debug it?

**Strong answer:** First find where it starts: log the loss, the gradient norm and the largest absolute weight
or activation per step, and find the first step that is non-finite, and whether it was preceded by a growing
loss or gradient norm (that points at divergence) or came suddenly (that points at a bad operation or a bad
batch). For divergence: the learning rate is above the stable limit for the current curvature; check feature
scaling (a large unscaled feature raises the largest Hessian eigenvalue), lower the rate or add warm-up, and
use gradient clipping as a guard. For a sudden `nan`: look for `log(0)`, division by zero, `sqrt` of a negative,
`exp` overflow in a hand-written softmax or sigmoid, or `nan`/`inf` in the input batch; I would assert that each
batch is finite and use numerically stable library losses. Then reproduce on a small subset with a fixed seed,
turn on anomaly detection (`torch.autograd.set_detect_anomaly`) to locate the operation, and gradient-check any
custom code in float64.

**Weak answer:** "Lower the learning rate until it goes away."

**Why the weak one fails:** it might hide the symptom but does not find the cause; if the cause is a bad input
row, a `log(0)` or an unscaled feature, a smaller rate only delays it or slows training for nothing.

**Follow-up an interviewer would ask:** "The loss is finite but suddenly spikes every few thousand steps. What
would you look at?"

### 3. How do you choose a learning rate? What do the loss curves look like when it is too high or too low?

**Strong answer:** Too low: the loss decreases smoothly but slowly and is still sloping when you stop. Too high:
the loss is noisy and stalls at a high level, oscillates, or rises and becomes `nan` within a few steps; in the
quadratic picture, the rate exceeds $2/\lambda_{\max}$ for the steepest direction. In practice I standardize
inputs, then try rates on a log grid (for example $10^{-4}$ to $1$ in factors of about 3) for a short run each,
and pick the largest rate whose loss falls smoothly, or use a learning-rate range test that increases the rate
during one short run and picks a value somewhat below where the loss starts to blow up. Then I use a schedule
(warm-up, then decay) for the full run, and treat the rate as a hyperparameter validated on held-out data,
re-tuning it when the batch size or the optimizer changes.

**Weak answer:** "Use 0.001; that's the default for Adam."

**Why the weak one fails:** a default is a starting point, not a method; it ignores feature scaling, batch size,
model and optimizer, and gives no way to recognise a bad rate from the curves.

**Follow-up an interviewer would ask:** "If you double the batch size, what would you do with the learning rate,
and why?"

### 4. Why standardize features for gradient descent? Does it matter for least squares in closed form, or for trees?

**Strong answer:** Gradient descent's stable step is limited by the steepest curvature and its speed by the
flattest; their ratio is the condition number of the Hessian, which for linear models is
$\frac{2}{n}\mathbf{X}^\top\mathbf{X}$. Features in very different units, or far from zero, make that matrix badly conditioned
(a long narrow valley), so you need a tiny rate and many steps, and GD zig-zags. Standardizing makes features
comparable and roughly decorrelates them from the intercept, which rounds the valley: in the lesson's
one-feature example the condition number went from 161 to 1. The closed-form solution gives the same
predictions with or without scaling (it is invariant to rescaling columns), although conditioning still
matters numerically, so `lstsq` or QR is preferred. Trees split on thresholds of one feature at a time, so
monotone rescaling does not change them at all. With regularization (ridge, lasso) scaling *does* change the
answer even in closed form, because the penalty treats all coefficients alike. The scaler is fitted on the
training data only and shipped with the model.

**Weak answer:** "Standardization makes all features equally important."

**Why the weak one fails:** it is wrong (scaling does not change the information in a feature), and it misses
the actual reason: conditioning of the optimization problem. It also does not distinguish the cases where
scaling matters from those where it does not.

**Follow-up an interviewer would ask:** "Where exactly in a cross-validation loop do you fit the scaler, and
what goes wrong if you fit it on all the data?"

### 5. How do you verify a hand-derived gradient, and what can make a correct gradient fail the check?

**Strong answer:** A numerical gradient check: perturb each parameter by $\pm h$, compute the central difference
$\frac{\mathcal{L}(\theta + h) - \mathcal{L}(\theta - h)}{2h}$, and compare with the analytic gradient by relative error,
$\lvert a - b\rvert/\max(\lvert a\rvert, \lvert b\rvert)$. I do it in float64, with $h$ around $10^{-5}$, on tiny random inputs
(not zeros, and a random non-symmetric matrix where symmetry would hide a bug), for every parameter if it is
small or a random subset if not; below about $10^{-7}$ passes, above $10^{-4}$ is a bug. I also assert every
gradient has its parameter's shape. A correct gradient can still fail if: $h$ is too small (rounding) or too
large (truncation); the computation is in float32; an input sits near a kink such as ReLU at 0 or a `max`; the
loss has randomness such as dropout that differs between the two evaluations; or the loss has a branch that
the perturbation crosses. Conversely, the check cannot catch a gradient that is correct for a loss that itself
is wrong; that needs a test of the loss against a reference.

**Weak answer:** "Train the model and see if the loss goes down."

**Why the weak one fails:** a wrong gradient often still lowers the loss (a constant factor, or a direction with
a positive dot product with the true one), so this proves almost nothing and gives no location for a bug.

**Follow-up an interviewer would ask:** "How would you gradient-check a layer with ten million parameters?"

### 6. Compare batch GD, mini-batch SGD and single-example SGD. How does batch size affect training?

**Strong answer:** Batch GD uses the exact gradient over all $n$ examples: smooth, predictable, but each step
costs a full pass, so it is impractical for large $n$. Single-example SGD uses one example per step: very
cheap steps but very noisy gradients, and poor use of vectorized hardware. Mini-batch SGD, with $B$ of tens to
thousands, is the standard compromise: the gradient is an unbiased but noisy estimate of the full gradient,
whose noise shrinks roughly like $1/\sqrt{B}$, and a batch is a good fit for GPU parallelism. Larger batches give
more accurate gradients per step and allow larger learning rates, but give fewer updates per epoch and
diminishing returns, and memory limits the size. Smaller batches add noise that can help escape poor regions of
a non-convex loss but need smaller rates. With a constant rate SGD hovers near the minimum, so schedules decay
the rate. Data must be shuffled every epoch so batches are representative.

**Weak answer:** "SGD uses one sample, mini-batch uses some samples, and batch uses all; mini-batch is best."

**Why the weak one fails:** it defines the terms but explains none of the trade-offs (noise, cost per step,
hardware, learning rate, convergence) and gives no reasoning for the conclusion.

**Follow-up an interviewer would ask:** "Your GPU can only fit a batch of 8, but the recipe you are copying used
256. What do you do?"

### 7. What is convexity and why does it matter? Neural-network losses are not convex; what are the consequences?

**Strong answer:** A function is convex if the graph lies below every chord; for a twice-differentiable loss,
the Hessian is positive semi-definite everywhere. Then every local minimum is global, so any correct optimizer
reaches the same optimal loss from any start: results are reproducible, a difference between implementations
indicates a bug, and tuning is mostly about speed. Linear and logistic regression, ridge, lasso and SVMs are
convex. Neural-network losses are not (permuting hidden units alone gives many equivalent minima, and there are
saddle points), so the result depends on initialization, data order and hyperparameters. Practical
consequences: run several seeds and report the spread; compare models on averages, not single runs; fix seeds
and log configurations for reproducibility; initialization and learning-rate schedules matter. Empirically,
large networks trained with SGD usually reach minima of similar quality, which is why training works despite
the non-convexity, but there is no guarantee.

**Weak answer:** "Convex means there is one minimum. Neural networks are not convex, so they can get stuck in
local minima, which is why we use Adam."

**Why the weak one fails:** "one minimum" is imprecise (a convex function can have a flat set of minimizers),
the claim that Adam solves non-convexity is wrong, and it misses the practical consequences: variance across
seeds and how to compare runs.

**Follow-up an interviewer would ask:** "Is the loss of logistic regression still convex if you add an L1
penalty? Is the optimum still unique?"

### 8. What is a Lagrange multiplier, intuitively, and where does it appear in ML?

**Strong answer:** To minimize $f$ subject to $g(\mathbf{x}) = c$, the optimum is where you cannot improve $f$ by moving
along the constraint, which means $\nabla f$ is perpendicular to the constraint surface and so parallel to
$\nabla g$: $\nabla f = \lambda\nabla g$. The multiplier $\lambda$ is a shadow price: $df^\star/dc = \lambda$, how much the best
achievable objective changes per unit of relaxing the constraint. For inequality constraints the KKT conditions
add $\mu \ge 0$ and complementary slackness: either the constraint is active or its multiplier is zero. In ML:
the SVM is a constrained margin maximization, and in its dual the multipliers are non-zero only for support
vectors; ridge and lasso can be written as minimizing the loss subject to a norm budget, with the regularization
strength playing the multiplier's role; maximum-likelihood estimates of category probabilities use a multiplier
for "sum to 1"; constrained policy optimization and fairness constraints use them too.

**Weak answer:** "It's an extra variable you add to handle constraints in optimization; SVMs use it."

**Why the weak one fails:** it describes the bookkeeping, not the idea (parallel gradients, shadow price), and
cannot explain *why* SVMs depend only on support vectors.

**Follow-up an interviewer would ask:** "Write the constrained form of ridge regression. How is the budget
related to the usual $\lambda$?"
