## Part 1: Self-test

1. **Central differences have error $\propto h^2$ instead of $\propto h$, so at the same step they are far more
   accurate (about $10^{-10}$ instead of $10^{-6}$ relative at their best steps).** A tiny step is worse
   because of rounding: $f(x + h)$ and $f(x)$ each carry an error of about $\varepsilon\lvert f\rvert$, and
   dividing their difference by $h$ amplifies it to $\approx \varepsilon\lvert f\rvert/h$. At $h = 10^{-12}$ that is
   about $10^{-4}$ relative; the total error is U-shaped with its bottom near $h \approx 10^{-5}$ to $10^{-6}$
   for central differences. *Revisit: A4.1.*
2. **Direction: steepest increase; length: the slope in that direction. $-\nabla f$ is steepest
   *decrease*, perpendicular to the contour line through the point, not a pointer to the minimum.** In a
   long, thin valley the contour lines are long ellipses, so the perpendicular points mostly across the
   valley (towards the near wall), not along it towards the minimum: gradient descent zig-zags.
   *Revisit: A4.2, A4.4.*
3. **Reverse mode gets the derivative of one output with respect to all inputs in one backward pass
   (about the cost of one more forward pass); forward mode and finite differences need one pass per
   parameter, $10^7$ passes.** The memory cost: every node's local derivative needs values from the forward
   pass, so all intermediate activations must be cached until the backward pass reaches them, which is
   why training needs far more memory than inference. *Revisit: A4.3.*
4. **Each eigen-direction of the Hessian contracts by $\lvert 1 - \eta\lambda_j\rvert$ per step; stability needs
   $\eta < 2/\lambda_{\max}$, so the flattest direction moves by at most about $2\lambda_{\min}/\lambda_{\max} = 2/\kappa$ per
   step, and the step count grows like $\kappa$.** Unscaled features (one in thousands, one in fractions, or a
   large mean next to the ones column) make $\kappa$ huge. Standardizing centers features (orthogonal to the
   ones column) and equalizes their scales, which shrinks $\kappa$, in the A2.4 example from 161 to 1.
   *Revisit: A4.4.*
5. **For a convex loss every local minimum is a global minimum, so gradient descent (with a stable step)
   reaches the best value from any start; with strict convexity the minimizer is unique.** The MSE of a
   neural network's output is not convex in the weights: the MSE is convex in the *prediction*, but the
   prediction is a non-linear function of the weights, and a convex function of a non-linear map need not
   be convex (swapping two hidden units gives the same loss at two different weight settings, and the
   average of the two settings is usually worse). *Revisit: A4.5.*
6. **$f'(x) = 6x^2 - 1$, so $f'(1) = 5$. $f(1.1) = 1.562$, $f(0.9) = 0.558$. Forward $(1.562 - 1)/0.1 = 5.62$, error

   $\nabla f = 2\mathbf{A}^\top(\mathbf{A}\mathbf{w} - \mathbf{b})$, `(3,)`.** Each gradient has the shape of the thing it is the

## Part 2: Interview questions

### 1. Explain backpropagation to a software engineer. Why is it efficient?

**Strong answer:** A model's loss is computed by a chain of simple operations: matrix multiplies, adds,
activations, then the loss. Record that computation as a graph during the forward pass and keep every
intermediate value. Backpropagation walks the graph in reverse. It starts with "the loss changes 1 per
unit of loss" and, at each node, multiplies the incoming gradient by that node's local derivative, which
only needs the node's own cached inputs (an add passes the gradient through, a multiply scales it by the
other input). Where a value fed several nodes, the gradients coming back from each are added. That is the
chain rule applied systematically. It is efficient because one backward pass, costing about as much as
the forward pass, gives the derivative of the single scalar loss with respect to every parameter, whether
there are ten or ten billion; nudging parameters one at a time would need a forward pass per parameter.
The price is memory, since the cached activations must be kept until the backward pass uses them.

**Weak answer:** "Backpropagation propagates the error backward through the layers to update the
weights using gradient descent."

**Why the weak one fails:** it restates the name. It does not say what is propagated (gradients, by
the chain rule), how each step works (local derivatives times the incoming gradient), why it is cheap
(one pass for all parameters) or what it costs (memory), and it conflates computing gradients with
using them to update weights.

**Follow-up an interviewer would ask:** "Why do frameworks make you call `zero_grad()`?" (Gradients
accumulate with `+=` across backward calls, by design, for fan-out and gradient accumulation.)

### 2. Your training loss turns into `nan` after a few hundred steps. How do you debug it?

**Strong answer:** First find where it starts: log the loss, the gradient norm and the weight norms
every step, and check the input batch for `nan` or `inf` at the step it breaks (bad data is a common
cause). If the loss grows or oscillates before it becomes `nan`, the learning rate is too large for the
current curvature: lower it by 3–10×, add warm-up, or clip the gradient norm. Check feature scaling,
since one unscaled feature makes $\lambda_{\max}$ of the Hessian huge and the stable learning rate tiny.
Look for numerically unstable operations: `log(0)`, division by a value near 0, `exp` of a large
number, or a softmax written without subtracting the maximum; use the fused, stable library versions.
Reproduce on a small batch with a fixed seed and the anomaly detection a framework provides, so the
first operation that produced the `nan` is reported. Fix the cause rather than skipping `nan` batches.

**Weak answer:** "Lower the learning rate until the `nan` goes away."

**Why the weak one fails:** it may hide the symptom while leaving the cause (bad data, an unstable
`log`, an unscaled feature), and it gives no way to tell those causes apart. A tiny learning rate can
also make training uselessly slow.

**Follow-up an interviewer would ask:** "The loss is fine but the gradient norm spikes every few
hundred steps. What do you suspect?" (Outlier batches, a too-high learning rate for some layers;
gradient clipping and data checks.)

### 3. Batch GD versus mini-batch SGD versus batch size 1. Why mini-batches?

**Strong answer:** Batch gradient descent computes the exact gradient over the whole training set for
each step: accurate, but one step costs a full pass over the data, which is infeasible for large data.
SGD with batch size 1 uses one example per step: very cheap steps but very noisy gradients, and it uses
hardware poorly because one example cannot fill a vectorized or GPU computation. Mini-batch SGD averages
the gradient over, say, 32 to 512 random examples: an unbiased estimate of the full gradient with
noise that shrinks as the batch grows, and a batch that fills the hardware's parallelism. In practice it
reaches a good model with far less total computation than full-batch descent. With a constant learning
rate SGD keeps jittering around the minimum, so the rate is decayed over training; data is shuffled each
epoch so batches are not correlated.

**Weak answer:** "Mini-batches are used because the whole dataset does not fit in memory."

**Why the weak one fails:** memory is one reason, but it misses the main one (many cheap, unbiased,
slightly noisy steps beat few exact ones in total compute) and says nothing about noise, hardware
utilization or the need for a learning-rate schedule.

**Follow-up an interviewer would ask:** "If you double the batch size, what would you do with the
learning rate, and why?" (Noise falls, so a larger rate is often stable; a common heuristic is to scale
it up roughly in proportion and validate.)

### 4. How do you choose a learning rate? What do too high and too low look like?

**Strong answer:** Too high: the loss oscillates, jumps up, or becomes `inf`/`nan` within the first
steps, because for a quadratic each eigen-direction is multiplied by $1 - \eta\lambda$ and diverges once
$\eta > 2/\lambda_{\max}$. Too low: the loss decreases smoothly but slowly and is still sloping down when
training ends, or seems to plateau early because the flat directions barely move. To choose: standardize
features, then run short trials on a log grid (0.0001, 0.0003, 0.001, …) for a few hundred steps and
keep the largest rate that decreases the loss smoothly, or use a learning-rate range test that increases
the rate during one short run and watches where the loss starts to blow up. Then add a schedule (decay,
warm-up) and confirm on the validation loss, not only the training loss.

**Weak answer:** "Use 0.001, it is the default in Adam."

**Why the weak one fails:** defaults are a starting point, not a method; the answer gives no way to
recognise a bad rate from the loss curve and no procedure to find a good one for a new model or data.

**Follow-up an interviewer would ask:** "Why can the best learning rate change when you add a feature?"
(It changes the Hessian's eigenvalues, in particular $\lambda_{\max}$.)

### 5. How do you test a hand-written gradient?

**Strong answer:** Compare it with a numerical gradient computed by central differences,
$\frac{f(\theta + h\mathbf{e}_j) - f(\theta - h\mathbf{e}_j)}{2h}$ for each coordinate, in float64 with $h \approx 10^{-6}$. Use a
relative error $\lVert a - b\rVert/(\lVert a\rVert + \lVert b\rVert)$, expecting about $10^{-8}$ or less for a correct
gradient. Test at random points (not zeros or symmetric values, where wrong formulas can agree), with
distinct dimensions so transposes cannot hide, and away from kinks such as ReLU at 0. Include a
negative control: break the gradient on purpose and confirm the test fails. For large models check a
small version of the same code, or a few random directional derivatives instead of every coordinate.

**Weak answer:** "Train with it and see whether the loss goes down."

**Why the weak one fails:** a wrong gradient often still lowers the loss (a missing factor of 2 just
rescales the learning rate; a gradient that is wrong for a few parameters still helps on the others),
so this test passes many bugs and gives no location for the error.

**Follow-up an interviewer would ask:** "Why float64 for the check if the model trains in float16 or
float32?" (In float32 the best finite-difference accuracy is about $10^{-5}$, so correct gradients fail
tight tolerances.)

### 6. Why does feature scaling matter for gradient descent but not for closed-form least squares or trees?

**Strong answer:** Gradient descent's speed depends on the conditioning of the loss: for the MSE the
Hessian is $\frac{2}{n}\mathbf{X}^\top\mathbf{X}$, the stable learning rate is capped by its largest eigenvalue, and the
number of steps grows with the ratio of largest to smallest. Features on very different scales (or with a
large mean) make that ratio huge, so training crawls or diverges; scaling fixes it. The closed-form
solution solves the normal equations or a QR/SVD least-squares problem directly, and rescaling a feature
just rescales its coefficient by the inverse factor, so the predictions are identical (scaling can still
help numerical accuracy when the condition number is extreme). A decision tree splits on thresholds of one
feature at a time, and any monotone rescaling preserves the order of values, so the same splits exist.
Scaling also matters for regularized models and distance-based models (kNN, k-means), for different
reasons.

**Weak answer:** "Scaling is always good practice because large numbers are bad for models."

**Why the weak one fails:** it gives no mechanism, so it cannot explain why trees do not care, and it
misses the actual reason gradient descent cares (the condition number and the stable step size).

**Follow-up an interviewer would ask:** "Where must the scaler's mean and standard deviation come from?"
(The training split only, then applied to validation and test, to avoid leakage.)

### 7. What is a convex function, and why does it matter? Why does deep learning work anyway?

**Strong answer:** A function is convex if the straight line between any two points on its graph never
goes below the graph; for twice-differentiable functions that means a positive semi-definite Hessian,
non-negative curvature in every direction. It matters because every local minimum of a convex function is
global: gradient-based training reaches the best possible fit from any starting point, different runs agree,
and you can certify optimality by checking the gradient is zero. Linear regression, ridge, logistic
regression and SVMs are convex. Neural network losses are not, so results depend on initialization and
seeds and there are no global guarantees. Training works anyway because, empirically, in very
over-parameterized networks most local minima that SGD finds are about as good as each other on the
training loss, and the noise of SGD plus good initialization, normalization and learning-rate schedules
helps it avoid bad regions and saddle points. These are empirical observations and partial theory, not a
guarantee, which is why we run several seeds.

**Weak answer:** "Convex functions have one minimum, so they are easy. Deep learning works because we
have lots of data and GPUs."

**Why the weak one fails:** "one minimum" is imprecise (a convex function can have a flat set of
minimizers or none), it omits the reason convexity matters (local equals global), and the deep-learning
part gives no mechanism and no acknowledgement that it is an empirical rather than guaranteed result.

**Follow-up an interviewer would ask:** "Is logistic regression's loss strictly convex? What happens with
perfectly separable data?" (Without regularization the weights grow without bound and no minimizer
exists; a small L2 penalty makes it strictly convex with a unique answer.)

### 8. L2 regularization versus a constraint on the weights. What does the multiplier do?

**Strong answer:** Minimizing the loss subject to $\lVert\mathbf{w}\rVert^2 \le r^2$ and minimizing the loss plus
$\lambda\lVert\mathbf{w}\rVert^2$ are the same problem: the KKT condition of the constrained version,
$\nabla\mathcal{L} + 2\mu\mathbf{w} = \mathbf{0}$, is exactly the zero-gradient condition of the penalized version with
$\lambda = \mu$. Each radius $r$ corresponds to a penalty strength, with smaller $r$ meaning larger $\lambda$. The
multiplier has a concrete meaning: it is the rate at which the best achievable loss would improve if the
constraint were loosened by one unit, the shadow price of the constraint; it is zero when the constraint
is not binding. Geometrically, at the constrained optimum the loss's contour touches the ball, so the
loss gradient and the constraint's gradient are parallel and the multiplier is the ratio. In practice we
use the penalty because it keeps the problem unconstrained and we tune $\lambda$ by validation.

**Weak answer:** "L2 regularization adds the squared weights to the loss to prevent overfitting, and a
constraint limits the weights. They are both regularization."

**Why the weak one fails:** it describes each separately without the equivalence, which is the point of
the question, and says nothing about what the multiplier means or how $r$ and $\lambda$ correspond.

**Follow-up an interviewer would ask:** "What changes with an L1 constraint?" (The ball has corners on
the axes, so the contour often touches it at a corner where some weights are exactly zero: lasso gives
sparsity, [B2.2](../../lessons/B/b2_2_regularization.md).)
