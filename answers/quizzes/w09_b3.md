## Part 1: Self-test

1. **The misclassification rate is flat: many useful splits leave the number of mistakes unchanged, so the search
   sees zero gain and stalls.** Example (B3.1 Step 4): parent $(400, 400)$; split A gives $(300, 100)$ and $(100, 300)$, split B gives $(200, 400)$ and $(200, 0)$. Both leave 200 rows
   misclassified (rate 0.25). Gini: A $= 0.375$, B $= \frac34 \cdot \frac49 + 0 = 0.333$, so Gini prefers B. B is better because its right child is pure and finished, and
   the left child can be split further; Gini and entropy are strictly concave, so they reward any move towards purity. *Revisit: B3.1.*
2. **The variance of an average of $B$ trees with variance $\sigma^2$ and correlation $\rho$ is $\rho\sigma^2 + (1 - \rho)\sigma^2/B$; only the second term is divided by $B$.** The trees are trained on overlapping
   bootstrap samples of the same data, so $\rho > 0$ and the variance never falls below $\rho\sigma^2$, however many trees you add. Feature subsampling
   (each split considers only a random subset, about $\sqrt{d}$ features) lowers $\rho$, which lowers that floor. The cost: each tree is weaker
   (higher bias and higher $\sigma^2$), so there is an optimum `max_features`, not "as few as possible". *Revisit: B3.2.*
3. **Forest: deep trees built independently (in parallel) on bootstrap samples; averaging reduces variance, and the
   bias stays that of one deep tree (low). Boosting: shallow trees built in sequence, each fitted to the current
   residuals; adding trees reduces bias, and variance is controlled by the learning rate, subsampling and early
   stopping.** More trees than needed: a forest's error flattens and never gets worse, it just costs time; boosting keeps fitting the
   training data and slowly overfits, so the validation error eventually rises (the number of trees is a hyperparameter). *Revisit: B3.2, B3.3.*
4. **(1) It is computed on training data, so splits that fit noise count as much as splits that fit signal; a deep tree
   keeps splitting small nodes, where noise often wins by chance. (2) It favours features with many distinct values,
   which offer many more candidate thresholds than a binary flag.** Permutation importance measures how much the score drops when a
   feature's link to the target is broken. On training rows, a model that memorized the noise column loses accuracy when
   it is shuffled, so the noise looks important (B3.4 lab: 0.017 on training rows, $-0.001$ on validation rows). Held-out rows measure
   reliance that generalizes. *Revisit: B3.4.*
5. **(1) A regularized objective, $\Omega(f) = \gamma T + \frac12\lambda\lVert\mathbf{w}\rVert^2$ per tree: $\gamma$ makes every leaf pay for itself (built-in pruning), and $\lambda$ shrinks leaf values, especially for leaves backed by few

## Part 2: Interview questions

### 1. How does a decision tree choose a split on a numeric feature? How do you stop it overfitting?

**Strong answer:** For every feature, sort the node's rows by that feature and consider a threshold between each pair of
neighbouring distinct values (CART uses the midpoint). For each threshold, compute the impurity of the two children,
Gini $1 - \sum p_k^2$ or entropy for classification, variance for regression, weighted by child size; pick the feature and threshold
with the largest drop from the parent. With the rows sorted, the class counts on the left are a running sum, so all
thresholds cost one pass: $O(m \log m)$ per feature per node. Recurse into both children. Greedy, so not globally optimal. Left alone it
grows until the leaves are pure and memorizes the data, so limit `max_depth`, require a `min_samples_leaf` of, say, 5–50, or
prune with cost-complexity pruning (`ccp_alpha`), choosing these by cross-validation. In practice I would use an ensemble instead of one deep tree.
**Weak answer:** "It tries the features and picks the one with the most information gain, then keeps going until the
leaves are pure. To avoid overfitting you prune it."
**Why the weak one fails:** no thresholds, no weighting by child size, no idea of how the search is done efficiently, and
"prune it" without saying how or how the setting is chosen.
**Follow-up an interviewer would ask:** "Why don't trees need feature scaling, and what kinds of relationships do they
represent badly?"

### 2. Why does a random forest generalize better than a single tree? What is out-of-bag error, and when would you not trust it?

**Strong answer:** A deep tree has low bias but high variance: retrain it on slightly different data and it changes a
lot. A forest averages many deep trees, each trained on a bootstrap sample and restricted to a random subset of features at
each split. Averaging cuts variance; the variance of the average is $\rho\sigma^2 + (1 - \rho)\sigma^2/B$, so the feature subsampling matters because it lowers
the correlation $\rho$ between trees, which bagging alone cannot remove. Bias is unchanged, which is why the trees are deep. Each bootstrap
sample leaves out about 37% of the rows, $(1 - 1/n)^n \to 1/e$; scoring every training row with only the trees that did not see it gives the out-of-bag
estimate, a free validation score. I would not trust it when rows are not independent, such as several rows per
customer or time-ordered data: a row's "unseen" trees saw its siblings or its future, so OOB is optimistic, just like
random k-fold. Then I would use grouped or time-based validation.
**Weak answer:** "Many trees vote, so errors cancel out. OOB error is the error on the data left out of training, so it
is like a test set."
**Why the weak one fails:** it misses the correlation argument (why feature subsampling exists), and "like a test set" ignores
the dependence problem and the fact that OOB is not a final test score.
**Follow-up an interviewer would ask:** "If I double the number of trees from 500 to 1,000, what happens to accuracy and
to overfitting?"

### 3. Explain gradient boosting. Why fit residuals, what does the learning rate do, how do you choose the number of trees?

**Strong answer:** Boosting builds an additive model $F_M = F_0 + \eta\sum f_m$. Start from a constant (the mean); each round fits a shallow tree to the
current residuals and adds a fraction $\eta$ of it. Fitting residuals is gradient descent in function space: for squared error
the residual is the negative gradient of the loss with respect to each prediction, and the tree is the closest function to
that gradient step that generalizes to new inputs. For other losses you fit the negative gradient, the pseudo-residuals,
for example $y - p$ for log-loss, with Newton-step leaf values. The learning rate shrinks each tree's contribution, so no single tree's fit to noise
dominates and later trees can correct earlier ones; a smaller rate generalizes better but needs proportionally more
trees. The number of trees is chosen by early stopping: train with a low rate and a high cap, monitor a held-out set
(not the test set), and stop after, say, 100 rounds without improvement. Depth controls the interaction order, typically 3–8.
**Weak answer:** "Each new tree corrects the errors of the previous ones. The learning rate controls how fast it learns.
You pick the number of trees with grid search."
**Why the weak one fails:** no connection to gradients or to other losses, no explanation of *why* shrinkage helps, and no
early stopping or held-out data.
**Follow-up an interviewer would ask:** "What happens to the validation curve if the learning rate is 1.0?"

### 4. 500,000 rows, 60 features: random forest or gradient boosting first? What would change your mind?

**Strong answer:** I would start with a simple baseline (a linear model or the majority class) and then gradient boosting
with LightGBM or XGBoost: on tabular data of this size it is usually the most accurate, it trains in seconds to minutes
with histograms, handles missing values natively, and early stopping takes care of the number of trees. A random forest is
the easier model to get right: fewer sensitive hyperparameters, no early stopping, embarrassingly parallel. So I would
also run one as a sanity check; if the two are within noise, the forest's robustness may win. I would change my mind
if: the data is tiny or very noisy (forest, or regularized linear); I need predictions to extrapolate a trend (neither: use a trend
model or detrend first); the model must be a readable formula (logistic regression); or the inputs are images, audio or text
(neural networks). Whatever I pick, the comparison is cross-validated with the same splits, and differences are judged against
the seed-to-seed spread.
**Weak answer:** "Gradient boosting, because it always wins on Kaggle."
**Why the weak one fails:** no baseline, no reasoning about the trade-offs (tuning effort, robustness, extrapolation), and no
plan to compare fairly.
**Follow-up an interviewer would ask:** "Which three hyperparameters would you tune first for LightGBM, and in what order?"

### 5. What does XGBoost do differently from the original gradient boosting machine?

**Strong answer:** On the learning side, two things. First, it adds a penalty to each tree's objective,
$\gamma T + \frac12\lambda\lVert\mathbf{w}\rVert^2$: a cost per leaf and an L2 penalty on leaf values. Second, it approximates the loss to second order around the current predictions, so with
$g_i$, $h_i$ the first and second derivatives, the objective for a fixed tree structure separates into one parabola per leaf. That gives the leaf value
$w^* = -G/(H + \lambda)$, a score for the whole tree, and a split gain $\frac12\big[\frac{G_L^2}{H_L + \lambda} + \frac{G_R^2}{H_R + \lambda} - \frac{(G_L + G_R)^2}{H_L + H_R + \lambda}\big] - \gamma$, so pruning is built into the criterion, and any twice-differentiable loss
works with the same code. It also uses shrinkage and column subsampling, and learns a default direction for missing
values at every split (sparsity-aware split finding). On the systems side: approximate split finding with a
Hessian-weighted quantile sketch, pre-sorted column blocks for parallel scans, cache-aware access, and out-of-core
blocks for data larger than memory. Since then histogram-based split finding (LightGBM, XGBoost's own `hist`) has become standard.
**Weak answer:** "XGBoost is a faster implementation of gradient boosting with regularization and parallel processing."
**Why the weak one fails:** it names the buzzwords but not what the regularization is, the second-order idea, or how missing values are
handled, which is what the question probes.
**Follow-up an interviewer would ask:** "What does `min_child_weight` mean for a log-loss model, in terms of $h_i$?"

### 6. A customer asks why your model denied their application. How do you produce an explanation, and what are its limits?

**Strong answer:** For a tree ensemble I would compute SHAP values for that application with TreeSHAP: one contribution
per feature, summing exactly to the difference between this applicant's score and a base value. The base value is the
average score over a background population that I choose deliberately, for example approved applicants. I would map the most negative
contributions to plain-language reasons, group correlated features (all the debt measures together), and drop
features the applicant cannot act on or that are sensitive, while checking the regulatory requirements for adverse-action
notices. Limits: SHAP explains the model, not the world. "Your debt ratio lowered your score" is true of the model; it does not
mean the debt ratio causes default. Values depend on the background, correlated features can share or swap credit, and
explanations can change between model versions. So I would test their stability across versions and log them with the
model version.
**Weak answer:** "Use SHAP and send the top three features with the biggest values."
**Why the weak one fails:** no base value or background, no handling of correlated or non-actionable features, no
distinction between explanation and causation, no stability or compliance consideration.
**Follow-up an interviewer would ask:** "How would the explanation change if you used the whole applicant population as
the background instead of approved applicants?"

### 7. Your model's feature-importance chart shows `account_id` in the top three. What do you do?

**Strong answer:** Treat it as a bug until proved otherwise. First, which importance is it? A tree library's default
impurity or gain importance is computed on training data and favours high-cardinality features, so an ID with
thousands of unique values can rank high just by memorizing training rows. Check permutation importance on a held-out
set: if it drops to about zero, the model memorized IDs and the feature should be removed, since it cannot generalize to new
accounts. If it stays high on held-out data, look for a leak or a structural artefact: IDs assigned in time order
(newer accounts behave differently), IDs reused across train and validation (rows from the same account in both, so
use a grouped split), or IDs that encode something like region or account type. Then drop the column, or replace it with the legitimate signal it was standing in for, retrain, and
compare validation scores, which should drop only slightly if the ID was a leak. Add a check to the pipeline that
blocks identifier columns.
**Weak answer:** "The model found that account_id is predictive, so keep it, or remove it because IDs are random."
**Why the weak one fails:** neither investigates. It does not distinguish impurity bias from leakage, does not check on
held-out data or for group leakage, and does not reason about what the ID might encode.
**Follow-up an interviewer would ask:** "Permutation importance on validation is high too. What would you check next?"

### 8. Great offline validation, clearly worse in production. How do you investigate?

**Strong answer:** I would work from the evaluation outwards. (1) *Was the offline score honest?* Look for leakage: features
computed with information from after the prediction time; a random split on time-ordered or grouped data; early stopping or
tuning on the set I reported (B1.4, B4.3). Rebuild the evaluation with a time-based split that mimics production and see
if the gap appears offline. (2) *Training–serving skew:* compare the feature distributions the model sees in production with
the training data, row by row for a sample. Different code paths, units, default values for missing data (XGBoost treats `NaN`
and 0 differently), category encodings, or stale features from a feature store. (3) *Drift:* has the population or the
target relationship changed since the training window? Monitor input distributions and the score distribution (J2.2).
(4) *The metric itself:* is the production metric the same as the offline one, on the same population and with the same
threshold? Delayed labels can make early production numbers misleading. I would fix the root cause, add tests for skew,
and set up monitoring and a retraining schedule.
**Weak answer:** "The model is overfitting. I would add regularization, tune hyperparameters again and retrain on more
recent data."
**Why the weak one fails:** it jumps to a fix without diagnosing; the most common causes (leaky validation, skew, drift)
would not be solved by regularization.
**Follow-up an interviewer would ask:** "How would you detect training–serving skew automatically before deployment?"
