## Part 1: Self-test

1. **Training fits the parameters, validation chooses between models and settings, and test measures the one
   final choice once.** With two splits, the set you choose on is also the set you report, so the report is biased.
   Picking the best of 60 test scores is exactly that: the winner is partly the model that got lucky on those test
   rows, so the reported score is **too high** (optimistic), and a fresh sample would give less. The fix is to choose
   on validation (or cross-validation) and touch the test set once; the inflation grows with the number of looks
   and shrinks with the size of the test set. *Revisit: B1.1.*
2. **The variance shrinks (by the factor $1 - \pi$, here to 70%) and correlations with other columns are pulled towards
   zero,** because 30% of the rows sit on one value that moves with nothing else. The fact of missingness carries
   information when *why* a value is missing is related to the target (in the lab, customers whose session count was
   missing churned at 57%, against 20% for the rest). Keep it with
   a **missing indicator** column (`SimpleImputer(add_indicator=True)`), and fit the imputer on training rows only.
   *Revisit: B1.2.*
3. **Train/serve skew is a feature computed one way for training and another way at serving time, so the model
   sees a different distribution in production.** Example: training SQL computes `days_since_signup` with
   `CURRENT_DATE` (the day the query ran), while the service uses the request time; or SQL treats `NULL` as 0 and the
   app code as missing; or the training job uses a 30-day window ending at month end and the service a rolling one.
   Prevention: one feature function (or a feature store with point-in-time joins) used by both paths, every
   training row computed "as of" its prediction timestamp, and a test that runs sample entities through both paths
   and asserts equal values. *Revisit: B1.3.*
4. **Target leakage** (a feature that encodes the answer, such as `retention_call` in a churn table; catch it by
   asking when each column is written and with single-feature AUCs that are too good); **train/test contamination**
   (a fitting step that saw the test rows, such as feature selection or target encoding on all rows; catch it by
   putting every fitted step in a pipeline and checking that refitting on training rows only does not change the
   score); **temporal leakage** (training on the future, such as a random split when the model predicts for later
   customers; catch it with a time-based split that mirrors deployment). The scaler learns only a mean and a
   standard deviation per column, nothing about the labels, so it barely changes the score (0.0000 in the lab);
   feature selection learns *which columns correlate with the labels, test labels included*, so it picks noise
   that happens to match the test labels (AUC 0.88 on pure noise, against 0.49 when done properly). *Revisit: B1.4.*
5. **The normal equations (and `LinearRegression`'s least-squares solver) solve for the minimum directly; scaling
   changes the units of the weights but not the solution or the predictions.** Gradient descent moves step by step
   on the loss surface, whose shape is set by $\mathbf{H} = \frac2n\mathbf{A}^\top\mathbf{A}$. Raw features with very different scales make $\kappa = \lambda_{\max}/\lambda_{\min}$
   huge ($5 \times 10^7$ on diabetes): the learning rate must be below $2/\lambda_{\max}$ to avoid diverging, and then the flat
   directions shrink by only $(\kappa - 1)/(\kappa + 1)$ per step, so they never converge in practice. Standardizing makes every
   diagonal curvature 2 and decouples the bias, cutting $\kappa$ to 370 there. *Revisit: B1.5, A4.4.*
6. **SE $= \sqrt{0.7 \times 0.3/400} = \sqrt{0.000525} = 0.0229$. $k = 10$: $0.70 + 1.54 \times 0.0229 = 0.735$. $k = 100$: $0.70 + 2.51 \times 0.0229 = 0.758$.** None of the
   models is better than 0.70; the best of 100 test scores is expected to overstate by almost 6 points. (The estimate
   treats the $k$ scores as independent; variants evaluated on the same rows are correlated, which makes the
   inflation somewhat smaller, but it does not remove it.) *Revisit: B1.1.*
7. **Observed mean 5; deviations $-3, -1, 1, 3$; variance $20/4 = 5$. After imputation the two new values sit at 5 and add
   nothing to the sum of squares: $20/6 = 3.33$.** $\pi = 2/6$, and $(1 - \frac13) \times 5 = 3.33$. *Revisit: B1.2.*
8. **(a) $\theta = 2\pi \times 6/24 = \pi/2$: $(\sin, \cos) = (1, 0)$. Hours 23 and 1 are 2 hours apart on the circle, an angle of $30°$:
   distance $2\sin(15°) = 0.518$, the same as hours 1 and 3. (b) Mean 20; deviations $-10, 0, 10$; $\sigma = \sqrt{200/3} = 8.165$;
   $(50 - 20)/8.165 = 3.67$.** A raw hour would put 23 and 1 twenty-two units apart. The new value uses the training
   mean and standard deviation; refitting on it would be wrong. *Revisit: B1.3.*
9. **AUC $= 5/6 = 0.833$.** Pairs: 0.9 beats 0.5 and 0.3 (2); 0.6 beats both (2); 0.4 beats 0.3 but not 0.5 (1); $U = 5$ of $3 \times 2 = 6$.
   Ranks ascending: 0.3 → 1, 0.4 → 2, 0.5 → 3, 0.6 → 4, 0.9 → 5. $R_+ = 5 + 4 + 2 = 11$; $U = 11 - 3 \times 4/2 = 5$. *Revisit: B1.4.*
10. **(a) $\bar{x} = 1$, $\bar{y} = 3$; $dx = -1, 0, 1$, $dy = -2, -1, 3$; $w = 5/2 = 2.5$, $b = 3 - 2.5 = 0.5$. Predictions $0.5, 3, 5.5$; residuals $0.5, -1, 0.5$
    (sum 0); SSE 1.5, SST 14, $R^2 = 1 - 1.5/14 = 0.893$. (b) $w = 12/4 = 3$ per raw unit, $b = 50 - 3 \times 10 = 20$.** Check: at $x = 10$ the
    standardized model gives $50 + 12 \times 0 = 50$ and the raw one $3 \times 10 + 20 = 50$. *Revisit: B1.5.*
11. **Prints `2 1`.** The test set has 5 rows. Stratified, it gets exactly $5 \times 4/20 = 1$ positive, the same 20% as the
    whole set; unstratified, the count depends on the seed (with this seed 2, i.e. 40%; other seeds give 1 or 2, and
    could give 0). `stratify` guarantees each split has (as nearly as rounding allows) the class proportions of the
    whole. With few positives, an unlucky split can leave a set with no positives at all, and every metric computed on
    it swings with the split. *Revisit: B1.1.*
12. **Prints `2.6666666666666665 4.5 [3.0, 5.0, 2.6666666666666665, 4.0, 2.6666666666666665, 6.0]`.** The first mean counts the
    sentinels as real values ($16/6$); the correct mean of the recorded values is $18/4 = 4.5$. The bug: `fillna(s.mean())`
    uses the mean of the *original* series, sentinels included, so the missing rows are filled with 2.67, a value
    lower than any real one. Replace the sentinel first, then compute the fill value from the cleaned column (and
    from training rows only), and add a missing indicator. *Revisit: B1.2.*
13. **Prints `[[0. 0.] [0. 1.] [0. 0.]]`.** With `drop="first"`, `basic` is the dropped reference category and encodes as all
    zeros; with `handle_unknown="ignore"`, the unseen `enterprise` also encodes as all zeros. So the model treats every
    `enterprise` customer exactly like a `basic` one, silently (apart from a warning that logs often swallow). Use
    `drop=None` (keep every column; regularized and tree models do not need the drop), so all zeros means
    "unknown" and nothing else, and monitor the share of unknown categories in production. *Revisit: B1.3.*
14. **Prints `0.85`** (anything clearly above 0.5 earns the point). The 20 columns were chosen because they correlate
    with *all* the labels, including the rows each fold later scores, so cross-validation measures how well noise
    fits noise that was selected to fit it: contamination through feature selection. Fix: put the selection inside
    the pipeline so each fold selects on its own training rows,
    `cross_val_score(make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression(max_iter=1000)), X, y, cv=5)`, which
    prints 0.48, chance level. *Revisit: B1.4.*
15. **`w` diverges: it prints about `[-1.29e+144 -3.01e+146]`.** $\frac2n\mathbf{A}^\top\mathbf{A} = \frac23\begin{pmatrix} 3 & 600 \\ 600 & 140000 \end{pmatrix}$; the largest eigenvalue is about
    $\frac23 \times 140{,}003 \approx 93{,}000$ (the second column dominates), so the step must be below $2/93{,}000 \approx 2.1 \times 10^{-5}$. With 0.01, each step
    multiplies the error along that direction by about $|1 - 0.01 \times 93{,}000| \approx 930$. Standardize the feature (or use the closed
    form). *Revisit: B1.5.*

## Part 2: Interview questions

### 1. Frame and evaluate a model that predicts which subscribers will cancel next month, before any model code.

**Strong answer:** First the decision: who acts on the prediction and how (say, the retention team calls the top 500
each week), because that fixes the prediction time, the horizon and the metric. Prediction time: the first of each
month; label: cancelled within the next 30 days; features: only what is known on the first. One row per subscriber
per month, built "as of" that date. Split by time (train on earlier months, validate and test on later ones),
and by customer if rows repeat, so evaluation mirrors deployment. Metric: precision in the top 500 or a cost-weighted
measure, plus ROC-AUC for ranking; check calibration if the scores are shown as probabilities. Baselines first: the
churn rate, and a one-rule model (for example "no login in 30 days"), so any model has a number to beat. Then data
checks: leakage review of every column, missing values, personal data minimized.
**Weak answer:** "I would collect all the customer data, train an XGBoost classifier with a random 80/20 split and
report accuracy."
**Why the weak one fails:** No prediction time, so leakage is likely; a random split ignores time; accuracy on a
5% churn rate is 95% for a model that predicts nobody churns; no baseline to compare against.
**Follow-up an interviewer would ask:** "How would you choose the 500, and how would you know the calls helped?"
(Ranking by score times expected value; a holdout group that is not called, because a model cannot measure its own
intervention.)

### 2. A fraud model reports 99.5% accuracy. What do you ask before believing it is useful?

**Strong answer:** What is the fraud rate? If 0.5% of transactions are fraud, predicting "not fraud" every time
scores 99.5%, so this number may mean nothing. I would ask for the majority-class baseline, then precision and recall
on the fraud class (or the precision–recall curve), because the business cares about how many frauds are caught and
how many good customers are blocked. I would ask how the split was made (by time and by card or account, since
fraud rings repeat), whether any feature is recorded after a chargeback (leakage), and how labels are produced
(chargebacks arrive weeks later, so recent "non-fraud" labels are incomplete). Then the cost of each error type, to
pick the threshold.
**Weak answer:** "99.5% is excellent; I would check for overfitting by comparing training and test accuracy."
**Why the weak one fails:** It never compares with the base rate, which is the first thing that makes 99.5% suspicious,
and the train/test gap says nothing about a useless model or about leakage.
**Follow-up an interviewer would ask:** "Which single metric would you put on the dashboard?" (Recall at a fixed
false-positive rate or precision at the review team's capacity, not accuracy.)

### 3. How do you handle missing values in a tabular dataset?

**Strong answer:** It depends on why they are missing and what model I use. First I find the missing values
that do not look missing: sentinels like −1, 0, 999 or "N/A" strings. Then I ask why each is missing: by design (no
second purchase yet), by failure (a sensor outage), or related to the target (sick patients skip a test). If it is
related to the target, the missingness is a signal and I add an indicator column. For the values themselves: a median
or mean fill with an indicator is a fine default for linear models; tree libraries such as gradient boosting can handle
`NaN` natively; dropping rows is fine only if few are missing and they are missing at random, since it biases the
data otherwise. Whatever I do is fitted on training rows inside the pipeline, and I check the missing rate in
production, since a jump usually means a broken upstream.
**Weak answer:** "I drop the rows with missing values, or fill them with the mean."
**Why the weak one fails:** No question about why values are missing, no sentinel check, no indicator; dropping rows
can remove exactly the cases that matter, and a mean computed on all rows leaks.
**Follow-up an interviewer would ask:** "What does mean imputation do to the variance and to correlations?" (Shrinks
the variance by $1 - \pi$ and weakens correlations.)

### 4. `[RAI]` Names, emails, postcodes, birth dates and a medical condition: what do you do with each? Is hashing the email enough?

**Strong answer:** Start from what the task needs. Names and emails are direct identifiers: the model does not need
them, so drop them. If I need a join key, replace the customer id with a keyed hash (HMAC) whose key lives in a
secret store, not a plain hash. Postcode and birth date are quasi-identifiers: harmless alone, identifying together
(Sweeney estimated that most of the US population is unique on ZIP code, sex and birth date), so coarsen them to what
the model uses, an age band and a postal district, and check that each combination covers enough people
(k-anonymity). The medical condition is a special category of data in laws such as the GDPR: keep it only if the task
needs it and access is restricted (VERIFY as of 2026-10, not legal advice). An unkeyed hash of an email is not
anonymous: anyone with a list of emails can hash them and match, and even a keyed hash is pseudonymous, still
personal data, because the key holder can re-identify.
**Weak answer:** "Hash all the identifiers with SHA-256 and the data is anonymous, so we can use everything."
**Why the weak one fails:** Unkeyed hashes of guessable values are reversible by lookup, the quasi-identifiers stay
identifying, and "use everything" ignores minimization and the sensitive column.
**Follow-up an interviewer would ask:** "How would you check whether coarsening was enough?" (Count the rows per
combination of quasi-identifiers and look at the smallest groups.)

### 5. What is train/serve skew, and how do you prevent it?

**Strong answer:** It is when a feature is computed differently in training and in production, so the model gets
inputs it never saw during training, and offline scores stop predicting live performance. Typical causes: two
implementations of the same feature (SQL for the training set, application code for serving) that disagree on nulls,
time zones or windows; training features computed with the current date instead of the prediction date; a
preprocessing step (scaler, vocabulary) refitted in one path and not the other. Prevention: ship preprocessing with the
model as one fitted pipeline; compute features in one shared function or a feature store with point-in-time joins;
log the features the service actually used and build the next training set from those logs; a parity test that runs
sample entities through both paths; and monitoring that compares live feature distributions with training ones.
**Weak answer:** "It is when the data changes over time; we retrain the model regularly."
**Why the weak one fails:** That describes drift. Skew is a bug in how features are produced, and retraining with the
same pipeline keeps it.
**Follow-up an interviewer would ask:** "How do you tell skew from drift in monitoring?" (Skew shows from day one
and on the same entities; drift grows over time.)

### 6. 0.95 AUC offline, barely better than chance in production. How do you debug it?

**Strong answer:** A gap that large is almost always leakage or skew, not ordinary drift. I would check, in order:
(1) leakage: for each top feature, when is it written relative to the prediction time? Single-feature AUCs that are
too good, and a retrain without the suspects, point to it; (2) the split: was it random when production predicts the
future, or did the same customers appear in train and test? Re-evaluate with a time split and a group split; (3)
fitted steps outside the pipeline (target encoding or feature selection on all rows); (4) skew: compute the features
for some live requests through the training path and compare with what the service sent; (5) the live label and
metric: is "production" measured on the same population, with the same label definition and delay? The honest
offline number after the fixes is usually what production shows.
**Weak answer:** "The data distribution changed; retrain on recent data and maybe tune hyperparameters."
**Why the weak one fails:** It assumes drift without evidence, and retraining with the same leak reproduces the same
inflated offline number.
**Follow-up an interviewer would ask:** "Which feature-importance pattern makes you suspect leakage?" (One feature
dominating everything, especially one that sounds like an outcome.)

### 7. Explain target encoding. How does it leak, and how do you do it safely?

**Strong answer:** Target encoding replaces a category (a postcode, a merchant id) with the mean of the target for
that category, which turns a high-cardinality category into one number. It leaks in two ways. If the means are
computed over all rows, each test row's value includes its own label: contamination. If they are computed on training
rows and applied to the same rows, each training row's value includes its own label, so on training data the feature
looks much more predictive than it is, and the model over-trusts it; on new data it can do worse than without the
feature. The safe way: out-of-fold encoding for training rows (each fold encoded with means from the other folds), means
from all training rows for validation and test, a fallback to the global mean for unseen categories, and smoothing
towards the global mean for small categories. scikit-learn's `TargetEncoder` does the cross-fitting in `fit_transform`
(VERIFY as of 2026-10, scikit-learn 1.9.1).
**Weak answer:** "You replace each category with the average label, which works well for high-cardinality columns.
Add smoothing to avoid overfitting."
**Why the weak one fails:** It never says the row's own label must be excluded; smoothing reduces the damage for small
categories but does not remove the leak.
**Follow-up an interviewer would ask:** "How would you encode a time-ordered problem?" (Use only earlier rows for each
row's encoding: an expanding mean.)

### 8. Closed form or gradient descent for linear regression? What changes for gradient descent?

**Strong answer:** The closed form solves the normal equations $\mathbf{A}^\top\mathbf{A}\boldsymbol{\theta} = \mathbf{A}^\top\mathbf{y}$ in one step (with `solve`, `lstsq` or a QR-based
solver, never an explicit inverse). It costs about $nd^2 + d^3$ and is exact, so it is my default up to a few thousand
features with data that fits in memory. Gradient descent (or SGD) costs about $nd$ per pass, never forms a $d \times d$ matrix,
and works on streams and mini-batches, so it is the choice for very many features or rows or online training, and it
is what neural networks use. For gradient descent I must standardize the features (fitted on training data), because
its speed depends on the condition number of the Hessian; pick a learning rate below $2/\lambda_{\max}$; monitor the loss for
convergence; and convert weights back to raw units if they are reported. With collinear features the closed form is
unstable, and ridge regularization helps either way.
**Weak answer:** "Gradient descent is better because it scales; the closed form needs a matrix inverse, which is slow."
**Why the weak one fails:** It ignores that the closed form is faster and exact at ordinary sizes, recommends the
inverse that should never be computed, and misses scaling, which decides whether gradient descent works at all.
**Follow-up an interviewer would ask:** "Your gradient descent loss decreases and then plateaus well above
`LinearRegression`'s. What do you check?" (Feature scales and the condition number; the learning rate; convergence
tolerance.)
