1. **`uv.lock` records the exact resolved version of every package, including indirect dependencies;
   `pyproject.toml` lists only the direct ones.** Printing versions lets anyone reproducing a result

2. **A generator is a stream: the extra draw shifts every later number, so the split (and possibly the
   initialization) changes, and the accuracy with it.** Fix: create independent child generators per
   purpose, e.g. `data_rng, model_rng, plot_rng = np.random.default_rng(SEED).spawn(3)`, so draws for
   one purpose never move another. *Revisit: A1.1.*

   memory.** Basic slicing (`x[1:3]`, `x[:, 0]`) gives a view; fancy indexing with a list or a boolean

   sum of an all-missing group is 0.0 (SQL gives NULL; use `min_count=1`); an integer column becomes

   is False, so test with `isna()` (SQL: `IS NULL`). *Revisit: A1.3.*
5. **Euclidean when magnitude is meaningful, e.g. kNN on standardized tabular features where "spends
   twice as much" matters. Cosine when only direction carries meaning, e.g. text embeddings, where

6. **(a) `(8, 5)`; (b) `(5,)`; (c) error.** For (c), aligned from the right: 4 vs 3 on the last axis,

## Part 2: Interview questions

### 1. What is broadcasting in NumPy? Give an example where it causes a silent bug, and how you would prevent it.

**Strong answer:** Broadcasting lets NumPy combine arrays of different shapes by aligning shapes from
the right and virtually stretching size-1 axes, so `X - X.mean(axis=0)` subtracts a `(d,)` vector from
every row of an `(n, d)` matrix without copying. The danger is that it succeeds whenever the rule
allows, not when you meant it. Classic bug: predictions of shape `(n, 1)` minus targets of shape `(n,)`
broadcast to `(n, n)`, so the MSE averages every prediction against every target; the code runs, the
loss is wrong, and the model drifts to predicting the mean. I prevent it with shape assertions at
boundaries (`assert y_hat.shape == y.shape`), shape comments on every line that changes a shape,
`keepdims=True` when a reduction must broadcast back, and a unit test that a perfect prediction gives
loss 0.
**Weak answer:** "Broadcasting makes arrays the same size so you can add them. It is convenient and I
use it all the time."
**Why the weak one fails:** it gives no rule (right-alignment, size-1 axes), no failure example, and no
prevention; it treats a common source of silent bugs as pure convenience.
**Follow-up an interviewer would ask:** "What shape is `A[:, None, :] - B[None, :, :]` for `A` `(n, d)`
and `B` `(m, d)`, and what is the memory risk?"

### 2. Why is vectorized NumPy faster than a Python loop? When can vectorizing make things worse?

**Strong answer:** A NumPy array is one contiguous, typed block of memory, and a vectorized operation
runs a compiled loop over it, often using SIMD instructions and optimized BLAS for matrix products.
A Python loop instead dispatches every arithmetic operation through the interpreter, checks types and
allocates a Python float object per element, which is typically 10–100× slower. Vectorizing can make
things worse when it materializes huge intermediates: broadcasting a pairwise difference for 2,000 ×
2,000 points with 512 features builds a 16 GB array, where the norm trick (`‖a‖² + ‖b‖² − 2AB^T`) or
chunking keeps memory small. It can also hurt readability, and numerically the algebraic rewrite can
lose precision (the norm trick far from the origin).
**Weak answer:** "NumPy is written in C, so it is faster."
**Why the weak one fails:** it does not explain *why* (interpreter overhead per element, contiguous
memory, no per-element objects) or name any trade-off.
**Follow-up an interviewer would ask:** "How would you compute the distance matrix for 100,000 points
without running out of memory?"

### 3. How do you make an ML experiment reproducible? What can still differ between two runs with the same seed?

**Strong answer:** Pin the environment with a lockfile and print versions; version the data (a
snapshot or a hash); put every random choice under one seed: `np.random.default_rng(SEED)` passed
explicitly (spawned per purpose), `random_state` on scikit-learn estimators and splitters,
`torch.manual_seed`, Python's `random.seed`; save the config with the results; and report results
over several seeds, not one. Even then, runs can differ: multi-threaded or GPU reductions add floats
in different orders, and float addition is not associative, so last digits move; some GPU kernels are
non-deterministic unless you force deterministic algorithms; Python's string hashing changes `set`
iteration order unless `PYTHONHASHSEED` is fixed; and different hardware or library builds can give
different results.
**Weak answer:** "Set `np.random.seed(42)` at the top of the script."
**Why the weak one fails:** it seeds only NumPy's legacy global generator, ignores other libraries,
environment and data versioning, and claims bit-for-bit reproducibility that seeds alone cannot give.
**Follow-up an interviewer would ask:** "Your result changes in the third decimal across seeds. How do
you report it?"

### 4. You join `events` to `users` to add the country, and the row count goes up. What happened, how do you find it, how do you prevent it?

**Strong answer:** A left join onto a lookup table should keep the left row count, so the increase
means the key is not unique in `users`: some `user_id`s appear more than once (duplicates from a bad
load, history rows, or a join on the wrong column), and every event for those users is multiplied by
the number of matches, since inner-join rows are $\sum_k n_L(k)\,n_R(k)$. To find it:
`users["user_id"].value_counts()` filtered to counts above 1, then inspect those rows to understand
why they are duplicated. Prevention: `merge(..., validate="many_to_one")`, which raises instead of
duplicating; an assertion that the row count is unchanged after an enrichment join; a uniqueness
check (or a primary key) on the lookup table at load time; and deduplicating with an explicit rule
(e.g. the latest record per user) rather than `drop_duplicates()` on the joined result.
**Weak answer:** "Use `drop_duplicates()` after the join."
**Why the weak one fails:** it hides the symptom without finding the cause, may drop legitimate
identical events, and leaves the duplicated users with an arbitrary country.
**Follow-up an interviewer would ask:** "The duplicates are because users change country over time.
Which country should an event get?" (Answer: the one valid at the event's timestamp, a point-in-time
join.)

### 5. A numeric feature has 5% missing values. How do you decide what to do?

**Strong answer:** First understand *why* it is missing: a logging bug, a field that did not exist
before some date, a value that is missing because it is zero or not applicable, or something related
to the target (e.g. users who churned never filled it in). That decides everything. I check whether
missingness correlates with other columns, time or the label. If it is random and rare, dropping rows
or imputing a median is fine. If it is informative, I keep the information with an indicator column
plus an imputed value. If it is "not applicable", a domain value (often 0) may be correct. Whatever I
choose, imputation statistics are fitted on the training split only and applied to validation and
test, inside a pipeline, to avoid leakage, and I compare the model's performance on rows that had
missing values against the rest.
**Weak answer:** "Fill with the mean."
**Why the weak one fails:** it does not ask why the data is missing, ignores informative missingness,
and (as usually done) computes the mean on all the data, which leaks.
**Follow-up an interviewer would ask:** "How do tree-based models like gradient boosting handle missing
values natively?" (Covered in B3.3.)

### 6. How do you check whether a chart supporting a launch decision is misleading?

**Strong answer:** I check what the chart encodes and whether the visual change matches the data
change. For bar charts, the axis must start at zero, otherwise bar lengths exaggerate differences; I
can compute the lie factor (effect drawn / effect in data). For time series, I ask why this time range
and not a longer one, because any noisy series has windows that rise and fall, and I ask for the
period before the change and the normal week-to-week variation, so I can see whether the change is
outside the noise. I check units and labels, whether it plots raw counts that should be rates
(tickets per active user), whether a log scale is labelled, and whether there is a comparison group:
a before/after chart cannot separate the launch from everything else that changed that week.
**Weak answer:** "I'd check that the chart looks clean and the numbers are right."
**Why the weak one fails:** correct numbers can still be drawn misleadingly; it names no specific
check (axis origin, range selection, noise, rates, control group).
**Follow-up an interviewer would ask:** "Is it ever acceptable for a line chart's y-axis not to start at
zero?" (Yes: lines encode position and slope, not length, as long as the axis is labelled.)

### 7. Explain cosine similarity. Why do embedding search systems normalize vectors at storage time?

**Strong answer:** Cosine similarity is the dot product divided by the product of the two lengths,
$\frac{\mathbf{a}\cdot\mathbf{b}}{\lVert\mathbf{a}\rVert\lVert\mathbf{b}\rVert}$, which equals the
cosine of the angle between the vectors: 1 for the same direction, 0 for orthogonal, −1 for opposite.
It ignores length, which suits embeddings where direction carries meaning. If every stored vector and
the query are scaled to length 1, the denominator is 1, so cosine reduces to a plain dot product,
which is cheaper and is what fast inner-product indexes and matrix multiplication do well. And for
unit vectors $\lVert\hat{\mathbf{a}} - \hat{\mathbf{b}}\rVert^2 = 2 - 2\cos$, so Euclidean-distance
indexes give the same ranking. Normalizing once at write time means no per-query division.
**Weak answer:** "Cosine similarity measures how similar two vectors are, and normalizing makes the
values between 0 and 1."
**Why the weak one fails:** it gives no formula or geometric meaning, gets the range wrong (it is −1
to 1), and misses the real reason for normalizing (cosine becomes a dot product; rankings agree with
Euclidean).
**Follow-up an interviewer would ask:** "When would you *not* want to ignore vector length?"

### 8. Find the 10 most similar items to a query among 1 million 768-dimensional embeddings.

**Strong answer:** Brute force: normalize everything, compute one matrix-vector product of
`(1,000,000, 768)` by `(768,)`, and take the top 10 with `np.argpartition` (no need to fully sort).
That is $10^6 \times 768 \approx 7.7 \times 10^8$ multiply-adds, around 1.5 GFLOP per query, and the
matrix is about 3 GB in float32. On a laptop that is roughly tens of milliseconds to a few hundred per
query, memory-bandwidth bound, and it is exact. That is fine for batch jobs and low traffic. When
latency or queries per second matter, or the collection grows, I would use an approximate
nearest-neighbour index such as HNSW or IVF (in pgvector, FAISS or a vector database), trading a
little recall for large speed-ups, and I would measure that recall against brute force on a sample of
queries before shipping. Reducing dimensions or using float16/int8 quantization cuts memory too.
**Weak answer:** "Use a vector database; it is fast."
**Why the weak one fails:** no cost estimate, no understanding of what the database does, and no
mention of the exact-versus-approximate trade-off or how to measure recall.
**Follow-up an interviewer would ask:** "How do you choose HNSW parameters, and how do you know the
approximate search is good enough?" (Covered in I2.2 and I2.4.)
