## Part 2: Interview questions

### 1. Explain backpropagation to a software engineer who knows calculus but has never trained a network. How does its cost compare with a forward pass, and why does that matter?

**Strong answer:** A network is a chain of simple functions (matrix multiply, add a bias, apply an activation) ending in
one number, the loss. Training needs the derivative of that number with respect to every weight. Backprop applies the
chain rule backwards: start from $\partial\mathcal{L}/\partial\mathcal{L} = 1$ at the end, and at each operation multiply the incoming gradient by that operation's local
derivative and hand it to the operation's inputs, adding contributions when a value was used more than once. For a dense
layer it reduces to three matrix products: $\mathbf{X}^\top\boldsymbol{\Delta}$ for the weights, the column sum of $\boldsymbol{\Delta}$ for the bias and $\boldsymbol{\Delta}\mathbf{W}^\top$ for the layer below.
The backward pass costs about two forward passes regardless of the number of parameters, versus two forward passes *per
parameter* for finite differences; that asymmetry (reverse mode for a scalar output) is what makes training billions of
parameters possible. The price is memory: the backward pass needs the forward pass's intermediate values, so they are
stored until it runs.
**Weak answer:** "Backprop computes the error at the output and sends it back through the network to update the weights
with gradient descent."
**Why the weak one fails:** it describes the flow but not the mechanism (chain rule, local derivatives, accumulation),
mixes up computing gradients with the optimizer's update, and says nothing about cost or memory.
**Follow-up an interviewer would ask:** "Where exactly does the memory go in the backward pass, and how does gradient
checkpointing trade it for compute?"

### 2. Why do neural networks need non-linear activation functions? Why is ReLU the usual default, and what is its main failure mode?

**Strong answer:** Without a non-linearity every layer is affine, and a composition of affine maps is affine, so any depth
collapses to one linear layer with linear decision boundaries; the activation is what lets hidden layers build new
features (XOR needs it). Sigmoid and tanh saturate: their derivatives are near 0 for large inputs (sigmoid's is at most
0.25), so gradients shrink layer by layer. ReLU, $\max(0, z)$, has derivative exactly 1 for positive inputs, so it passes
gradients without shrinking them, is cheap, and gives sparse activations; a ReLU network is piecewise linear. Its failure
mode is the dead ReLU: a unit whose pre-activation is negative for every input outputs 0 and gets 0 gradient, so it never
recovers, typically after a large update from too high a learning rate or bad initialization. You detect it by measuring
the fraction of units that are never active on a batch; remedies are a lower learning rate, He initialization, or variants
like Leaky ReLU and GELU (the transformer default).
**Weak answer:** "Activations add non-linearity so the network can learn complex patterns. ReLU is fast and avoids
vanishing gradients."
**Why the weak one fails:** it does not explain *why* linearity is a limit (the collapse), and it omits ReLU's own failure
mode, which the question asks for.
**Follow-up an interviewer would ask:** "Is ReLU's non-differentiability at 0 a problem for gradient descent?"

### 3. How does PyTorch's autograd work under the hood? Why does `.grad` accumulate across `backward()` calls, and when is that accumulation actually useful?

**Strong answer:** Every operation on a tensor with `requires_grad=True` records a node (`grad_fn`) that holds references
to its inputs and whatever it needs for its backward rule. The graph is built during the forward pass, fresh each time
(define-by-run, so Python control flow works). `loss.backward()` walks the graph in reverse topological order from the
scalar loss, calling each node's backward function and adding the results into the inputs' gradients; leaf tensors with
`requires_grad` end up with `.grad` filled in, and the graph is freed. Gradients are *added* because a tensor used in several
places must receive the sum of all paths, and the same mechanism means a second `backward()` adds onto the first. That is
useful for gradient accumulation: run several small micro-batches, each calling `backward()` (with its loss divided by the
number of micro-batches), then take one optimizer step, to simulate a large batch that does not fit in memory. Otherwise
it is a bug source, hence `optimizer.zero_grad()` every step.
**Weak answer:** "PyTorch keeps track of operations and calculates gradients automatically. You have to call zero_grad
because otherwise it adds up."
**Why the weak one fails:** no graph, no order, no reason the design accumulates, and no legitimate use of accumulation.
**Follow-up an interviewer would ask:** "What does `.detach()` do to this graph, and when would you use it?"

### 4. Why are softmax and cross-entropy almost always implemented together? Derive the gradient with respect to the logits.

**Strong answer:** Two reasons, stability and simplicity. With $p_k = e^{z_k}/\sum_j e^{z_j}$ and $\ell = -\log p_y$, the log and the exponential cancel:
$\ell = \log\sum_j e^{z_j} - z_y = \operatorname{LSE}(\mathbf{z}) - z_y$. LSE is computed stably by subtracting the max logit, and no probability is ever formed, so
confidently wrong examples give the right large loss instead of $\log 0$. The gradient: $\partial\operatorname{LSE}/\partial z_k = e^{z_k}/\sum_j e^{z_j} = p_k$, and
$\partial z_y/\partial z_k = y_k$ (one-hot), so $\nabla_{\mathbf{z}}\ell = \mathbf{p} - \mathbf{y}$, divided by $n$ for a batch mean. Done separately, you would multiply by softmax's
`(K, K)` Jacobian $\operatorname{diag}(\mathbf{p}) - \mathbf{p}\mathbf{p}^\top$ and divide by $p_y$, which is slower, needs more memory and divides by a number that can be 0.
With two classes it reduces to logistic regression's $\sigma(z) - y$. In PyTorch this is why `CrossEntropyLoss` takes raw logits.
**Weak answer:** "Softmax gives probabilities and cross-entropy compares them to the labels. The gradient is the
prediction minus the label."
**Why the weak one fails:** states the result without the derivation the question asks for, and misses the stability
argument entirely.
**Follow-up an interviewer would ask:** "How does this change for label smoothing or soft targets?" (Still $\mathbf{p} - \mathbf{t}$.)

### 5. You wrote a custom layer with its own backward pass. How do you convince yourself and a reviewer that the gradient is correct?

**Strong answer:** A numerical gradient check, set up so that it can fail. Use float64, a small random input with
non-trivial shapes (not square, so transposes cannot hide), random non-zero biases, and a scalar loss that weights each
output differently (for example the sum of the output times a fixed random tensor), so errors cannot cancel. Compare
the analytic gradient for every input and parameter with central differences, $h \approx 10^{-6}$, using a relative error
$\lVert a - b\rVert/(\lVert a\rVert + \lVert b\rVert)$; below $10^{-6}$ passes, and $10^{-8}$ or less is typical. Avoid kinks (ReLU at 0, max at a tie), which make a correct gradient
look wrong. Include cases where a value is used twice and broadcast inputs. In PyTorch, wrap it as an
`autograd.Function` and run `torch.autograd.gradcheck` (which also wants float64). Then compare end to end against a
reference implementation built from standard operations, and keep the check as a unit test in CI so a later refactor
cannot silently break it.
**Weak answer:** "I'd check that the loss goes down when I train with it."
**Why the weak one fails:** a slightly wrong gradient often still lowers the loss (any direction with a positive dot product
with the true gradient does), so this test cannot detect most bugs.
**Follow-up an interviewer would ask:** "Your check fails with relative error $10^{-3}$ only for one bias. What are the likely
causes?"

### 6. Your training loss suddenly becomes `NaN` at step 4,000. Walk me through how you find and fix the cause.

**Strong answer:** First reproduce it cheaply: same seed, checkpoint from just before the failure if available. Then
find the first non-finite value rather than looking at the loss: log the loss, the gradient norm and the max absolute
activation or logit per step leading up to it (a steady climb points to divergence: learning rate too high, missing
gradient clipping, a warmup that ended), and run a short window with `torch.autograd.set_detect_anomaly(True)` or
`torch.isfinite` assertions in forward hooks to name the operation that first produced `NaN`/`inf`. Typical causes: a
hand-written `log(softmax)` or `log(p)` on a probability that underflowed, an `exp` that overflowed (especially in
float16), a division by a variance or norm that hit 0, a bad input batch (a `NaN` in the data), or a learning rate spike.
Fix the cause: use fused, stable losses on logits (`cross_entropy`, `BCEWithLogitsLoss`), add epsilons inside divisions and
square roots where they are meant to be, clip gradients, lower the learning rate or lengthen warmup, keep losses and
softmax in float32 under mixed precision, and validate the data. Do not just clip probabilities or skip `NaN` batches, which
hides the problem.
**Weak answer:** "Lower the learning rate and restart from the last checkpoint."
**Why the weak one fails:** it might work by luck but finds nothing, so the same failure returns, and it ignores numerical
bugs that no learning rate fixes.
**Follow-up an interviewer would ask:** "The `NaN` only happens with mixed precision. What is different there?"

### 7. What does the universal approximation theorem say? If one hidden layer is enough, why are networks deep?

**Strong answer:** For a suitable activation (sigmoid-like, and later results cover ReLU), a network with one hidden layer
can approximate any continuous function on a bounded region to any accuracy, given enough hidden units (Cybenko 1989,
Hornik 1991). It is an existence result: it says nothing about how many units are needed, whether gradient descent finds
the weights, or how well the network generalizes from finite data. The number of units can grow exponentially with the
input dimension or the complexity of the function. Depth helps because composition reuses computation: for example $L$
layers of 2 ReLUs compose a "tent" function into a sawtooth with $2^L$ linear pieces, while one hidden layer needs $2^L - 1$ units
for the same function. Deep networks also match the hierarchical structure of real data (edges, parts, objects), and in
practice they reach a given accuracy with far fewer parameters. The caveat: depth makes optimization harder (vanishing or
exploding gradients), which is why initialization, normalization and residual connections exist.
**Weak answer:** "It says neural networks can learn any function. Deep networks are better because they have more
parameters."
**Why the weak one fails:** "learn" is wrong (the theorem is about representation, not learning), and depth is not
about parameter count; a wide shallow network can have more parameters and do worse.
**Follow-up an interviewer would ask:** "With random initialization, does a deeper ReLU network actually have exponentially
more linear regions?" (No; at initialization the count grows roughly with the number of units.)

### 8. Why does training a network need much more memory than running it for inference? What can you do when training runs out of memory?

**Strong answer:** Inference only needs the weights and the current layer's activations; each intermediate tensor can be
freed once the next layer has used it. Training must keep every intermediate value the backward pass reads (layer inputs,
pre-activations, attention matrices) until `backward()` runs, plus a gradient for every parameter and the optimizer state
(Adam keeps two extra tensors per parameter), so memory grows with batch size × depth × width on top of about 3–4 times the
weights. When it runs out: reduce the batch size and use gradient accumulation to keep the effective batch; use mixed
precision (bf16/fp16 activations); use gradient (activation) checkpointing to store only some activations and recompute
the rest in the backward pass, trading about one extra forward pass for much less memory; shorten sequences or crop
images; use a smaller model or parameter-efficient fine-tuning (LoRA); and make sure evaluation runs under
`torch.no_grad()` and that no code keeps references to loss tensors (use `.item()`). Beyond one GPU, shard parameters,
gradients and optimizer state (FSDP/ZeRO).
**Weak answer:** "Training needs to store gradients. Use a smaller batch size."
**Why the weak one fails:** gradients are only part of it (activations usually dominate), and one remedy is not a plan; it
misses accumulation, checkpointing and precision.
**Follow-up an interviewer would ask:** "Roughly how much memory does Adam need for a 1-billion-parameter model in mixed
precision, before activations?"
